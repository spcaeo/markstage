Several server processes on one data dir

Run several Markstage server processes on one data dir and one machine: what they share, how locks and limits hold across them, and what is still limited.

On this page

  • How they share
  • Clock jumps and pauses
  • The audit: every piece of process memory in packages/server/src
  • What is still limited

Markstage may run as several markstage-server serve processes on one data dir, each on its own port, behind one address. They behave as one server: a person may sign in on one, and their next request may land on another. This page says what they share, how, and what is still limited. How to run them: DEPLOY.md, "Several server processes". The proof: packages/server/test/multi-process.test.mjs (two real processes on one data dir), test/cluster.test.mjs (the shared pieces) and e2e/two-process.e2e.mjs (signed in on one, editing on the other, in a browser).

How they share

  • The database. Everything that must hold across processes is in the data dir's SQLite database (markstage.db, WAL mode, a 5 second busy wait). Every count that a limit checks is read and written in one write transaction (BEGIN IMMEDIATE), so two processes never both see "one left" and both take it.
  • Leases. A lock with an owner, in the database (leases). Each process has a row in server_processes and a heartbeat (every sixth of processes.leaseSeconds: 5 seconds by default) that keeps it fresh. A lease is let go by its owner, or taken over by another process only once its owner has stopped (see "Clock jumps and pauses"): at once when the owner ran on the same machine and its pid is gone (a crash, kill -9), and for a process on another machine (another container) once its heartbeat stood still for a lease (30 seconds by default).
  • Fencing. Work done under a lease checks the lease is still its process's before each step: each job step, each git write (the repo lock file still names it), each webhook send, and each AI ask of a site translation. When it is not (another process took over while this one was paused), the work stops there and says so: the job fails with "Another server process took this over while this one was paused, so the job stopped here.", the server log says which lease was lost.
  • The repo lock file. Every write to the site repo (a save, a commit, a revert, a merge) holds <data dir>/repo.lock, made with an exclusive create (one process wins) and naming its owner: its process id, pid, when that pid started, and its machine. A lock left by a process that stopped is removed by the next process that wants it, judged by that pid and its start time (on another machine by its heartbeat), never by the file's age; the removal is decided inside the database's write transaction so two waiters never both remove it. Git's own optional locks are off for reads (GIT_OPTIONAL_LOCKS=0), so a git status on one process never trips a commit on another with index.lock.
  • The primary role. One lease, primary, held by one serve process. Its holder runs what must run once for the whole server: the scheduler, scheduled releases, backups, alert digests, the webhook timer, integration refreshes, form alert retries, the hourly sweeps, the preview listener with its dev server, and the share-link listener (both on their fixed ports). When it stops, another process takes the role at its next heartbeat. The first process to start takes it; the rest serve the editor and the API.
  • Stopped work. At a start with no other process running, the old restart rules apply as before (jobs failed, site translations paused). While others run, only the work of the process that stopped is marked: its jobs failed with "The server process running this job stopped.", its release builds and publishes, imports and branch previews failed, its site translation paused for anyone to resume, its in-flight AI asks and leases dropped.
  • Stepping down. A process that is stopping lets its roles go and never takes one back, even when a heartbeat runs while a role is still stopping (its preview dev server exiting, a webhook send ending). Its heartbeat stops first when it closes, so nothing runs on its behalf against a closed database.
  • Floods. A limit counts first and writes a try only when it lets it through, so a refused try costs no row. An IPv6 address counts as its /64 (one person usually holds a whole /64) for sign-in misses, wrong tokens and share-link tries. Tries whose window has passed are deleted at most a minute later, by the next process that writes one.

Clock jumps and pauses

The wall clock is not trusted to say a process stopped. It jumps: an NTP step, a VM paused and resumed, a laptop asleep, a process stopped with SIGSTOP for a while. Before, a jump of more than the lease made a live process look stopped, and another one took its job, its primary role and its repo lock while it was still working. Now:

  • On the same machine (the same hostname, and on Linux the same pid namespace and boot id), a process runs while its pid answers. Its row also keeps when that pid started (from /proc/<pid>/stat on Linux, ps -o lstart on macOS), so a new process that got the old pid is not taken for it. The heartbeat's age is only used to decide when to ask. A paused process keeps its leases and its lock however long it was silent; a hung one keeps them until it is stopped (systemd's TimeoutStopSec or a kill).
  • On another machine (another container), a process runs while its heartbeat moves. Once a process has seen it, it times it with its own monotonic clock, which does not jump: it counts as stopped only when its heartbeat stood still for a lease by that clock and by the wall clock. At the first sight (just after a start) the heartbeat's age decides, as before.
  • Fencing (above) covers what is left: a process on another machine that was paused for longer than the lease finds, when it wakes, that its lease or lock is someone else's, and stops before its next step.

The proof: test/cluster.test.mjs (clock jumps of 40 seconds and an hour, forward and back; a reused pid; another pid namespace with the same hostname; fencing; stepping down) and test/multi-process.test.mjs (a real process frozen with SIGSTOP for twice its lease keeps its primary role and its job, then finishes it).

What is still limited

  • One machine. All processes must run on one machine with the data dir on a local disk. SQLite's WAL mode does not work over a network file system, and the quick "its pid is gone" check only works for processes on the same machine. Several machines would need a database server; that is not built.
  • Docker. Two containers on one volume are not tested. Run several processes with systemd on one host (the supported way, DEPLOY.md), or one container per data dir. Containers that share a hostname are told apart by their pid namespace (Linux), so one never reads the other's pids; they judge each other by the heartbeat.
  • Taking over takes a moment. When the primary process stops cleanly, another takes the role at its next heartbeat (5 seconds by default, processes.leaseSeconds / 6); when it crashes on the same machine, the same. A process on the same machine that hangs, or is paused, without dying keeps its role until it is stopped (the role is never taken from a live process, so nothing runs twice); one in another container, after its heartbeat stood still for a lease (30 seconds by default). Meanwhile the preview and share hosts answer 502 from nginx, and the timers wait. The editor and the API go on, on the other processes.
  • A process on another machine that wakes from a long pause stops its work at its next step (fencing), but a step already running when it froze (a build command, a webhook request in flight) ends as it would have.
  • A process that stops mid-job. Its job is failed and must be run again; a job still queued in it is failed too (it is not handed to another process). A site command it had started (a build) is not stopped by its crash and runs to its end, so the next build may start while that one finishes; a clean stop (SIGTERM) waits for the job first, as before.
  • Turns, not order. Jobs run one at a time across processes, each process's in the order it got them; between processes, whichever asks first when the lease frees goes next.
  • Small delays. A running job's log on another process is at most a second behind; an unsaved change pushed to another process reaches the preview within a second; Pause or Cancel of a site translation asked on another process takes effect between two asks (the answer waits up to 30 seconds for it).
