Markstage server: security

How the self-hosted Markstage server protects a content site: sign-in, sessions, two-factor, roles, previews on their own origin, and the test behind each.

On this page

  • Privacy (GDPR/PIPEDA)
  • Operator checklist
  • Known limits and follow-ups

How packages/server protects a content site, what each control is, and which test proves it. Tests live in packages/server/test/ and run with npm test in packages/server (node:test, a throwaway git fixture site per suite, the server on an ephemeral 127.0.0.1 port).

What we protect

  • The live site. Only a signed-in user with the right role can change what visitors see. A failed check, build or deploy never changes it.
  • The content repo. Writes touch only entry files inside configured collection folders, plus uploads inside the media folder. Each write is one git commit by the signed-in user, so nothing is lost and everything is attributable.
  • Accounts. Password hashes, sessions, 2FA secrets, recovery codes and page passwords live in the server's data dir, never in the repo or in a URL.
  • Protected pages. A page with a password is never in the public build output, and is served only after the page password is entered.

Out of scope for the server itself: the security of the machine, the reverse proxy's TLS setup, the site's own build scripts (the operator configures them), and rendering. The server's job there is to stop contributors from saving new raw HTML.

nginx recipe for protected pages (production)

The tested files are deploy/nginx/production.conf (TLS, two host names) and deploy/nginx/site.conf (compose); DEPLOY.md explains them. The security-relevant points:

  • The site host serves current/public; anything not found there goes through auth_request /markstage/page-auth (internal, X-Original-URI, the visitor's cookie). On 204 nginx serves the file from current/private with X-Robots-Tag: noindex and Cache-Control: private, no-store; on 401 Markstage shows the password form (or 404).
  • Use try_files $uri $uri/index.html @protected, not $uri/: the folder of a protected page can still exist in the public build (public child pages), and $uri/ makes nginx answer 403 instead of asking Markstage.
  • If Markstage is down, the auth subrequest fails and nginx answers 500: protected pages fail closed.
  • A request on the site host reaches only the page gate (the CMS API and editor answer 404 there). The CMS has its own host name, because authors can write raw HTML and the site origin must not hold the CMS session.
  • Set trustProxy: true so the gate's rate limit sees the visitor's address from X-Forwarded-For.

Dependencies

What the server runs on (checked against each package.json and the imports in src/, 2026-11-03):

  • Node built-ins for everything else: node:http, node:crypto (scrypt, HMAC), node:sqlite, node:child_process. No web framework, no database driver, no mail library.
  • @markstage/core (our own package, from this repo): the converter and the checks. It brings five small packages: yaml, unified, remark-parse, remark-gfm and decode-named-character-reference.
  • sharp (optional): Node has no image codec, and re-encoding is the reliable way to strip what is not pixels. Without it, picture uploads are refused (503) unless the operator turns re-encoding off (media.reencode: false).
  • node:sqlite prints an ExperimentalWarning on Node 22/24; the CLI hides that one warning only.

The policy (CONTRIBUTING.md, "Dependencies", has the full list for every package): the lockfile is committed and every install is npm ci; CI runs npm audit --omit=dev --audit-level=high and gitleaks on every push; a release is cut only from a clean npm audit --omit=dev; Dependabot proposes updates every week.

Known limits and follow-ups

  • Sign-in lockout: the trade-off. Wrong passwords lock only the (account, address) pair they came from. The account itself locks for everyone only after 50 misses in an hour from anywhere (login.accountMaxFailures, login.accountWindowSeconds), and even then a browser the person signed in from before, with the right password, still gets in. What is left: someone who sends 50 wrong passwords an hour from many addresses can keep the person out on a new device (a new laptop, or after clearing cookies) until the lock ends (login.lockMaxSeconds, 10 minutes by default) and again each hour. The way back at once: the owner or an administrator uses Reset password on the person (People & access), or the server's operator runs markstage-server reset-password <email>; the setup code that gives is not stopped by the lock, and signing in with it clears the lock (auth.test.mjs "locked out account-wide on a new device…"). A reset from the owner's own account needs that account to be signed in somewhere, so the owner should turn on 2FA and keep one known browser, or have shell access to the server.
  • Every signed-in role reads every entry, drafts included. A contributor or author can open any draft, its Markdown source and its revisions, not only their own; the roles limit who may change and publish, not who may read. This is on purpose (people see what the site is about to say, and links and Library items need it). Give an account only to people who may see unpublished work; a draft that must stay with a few people belongs outside the site repo until it is ready.
  • Two-step secrets are stored as they are. An authenticator app needs the TOTP secret itself, so the database keeps it as a plain value (passwords and recovery codes are hashed). Anyone who reads markstage.db or a backup of it can make that person's codes: protect the data dir and every backup like a password store (DEPLOY.md, Backups).
  • The per-IP sign-in limiter (login.ipMaxAttempts failed tries per login.ipWindowSeconds; successes never count and clear the address), the share-link and the environment-gate counters live in process memory: a restart forgets them (fine for windows of minutes) and a second server process would not share them, so those limits count per process. One markstage-server serve per data dir is assumed; the account and page lockouts are in the database and hold across restarts; the edge proxy's own limits (deploy/nginx: 10 sign-in POSTs a minute per address) cover a public site.
  • Audit rows for refused cross-site requests can grow under attack. There is no retention policy yet. The same goes for share.view rows: someone holding a working link can add rows until it expires or is turned off.
  • A synced Library item cannot go into a release (it rewrites every page that uses it when it changes); it goes live from the Library on its own.
  • Builds see the working tree as it is at build time. A draft saved during a build is not shipped (drafts are filtered), but a live entry saved by an editor during a build may be.
