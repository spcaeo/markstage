Conventions

  • Prefix /markstage/api/. All paths below are relative to it. Bodies and answers are JSON (Content-Type: application/json) unless a route says otherwise. Every answer has Cache-Control: no-store.
  • Ids are opaque. :c is a collection id from the site config (posts, pages, ...). :id is an entry id, which is the file name without extension and matches ^[a-z0-9][a-z0-9-]{0,99}$. Users, sessions, jobs, media, snippets, templates and trash items have random ids (u_…, s_…, j_…, m_…, sn_…, t_…, tr_…). No path, email or secret ever goes in a URL; secrets (setup codes) are typed by the person, never put in a link.
  • Session: an httpOnly cookie __Host-markstage (Secure, SameSite=Strict, Path=/). The client never reads it.
  • CSRF: every request that is not GET/HEAD needs the Origin header equal to the server's public origin, and (once signed in) X-CSRF-Token: <csrfToken> from GET auth/me or the login answer. The token changes at every sign-in. Routes marked (pre-auth) need the Origin check only.
  • Optimistic concurrency: every entry answer carries version = sha1 of the file text (hex). Every write to an entry sends the version it started from. If the file changed since, the answer is 409 {error:'conflict', message, version:<current>} and nothing is written.
  • Errors: {error, message} with a stable code. 400 bad-request, 401 unauthorized (no or expired session), 403 forbidden (signed in, not allowed), 404 not-found, 409 conflict, 413 too-large, 415 unsupported-type, 422 invalid (with fields: {name: message}), 423 locked (account lockout with retryAfter seconds, or a save that moves, deletes or changes a locked block, with blocks: see "Locks"), 429 rate-limited (Retry-After header), 500 server, 503 unavailable. A message is plain words for the writer; detail (optional) is for logs.
  • Times are ISO 8601 strings in UTC (2026-10-28T14:05:00.000Z).
  • Lists take page (1-based) and perPage (default 50, max 200) and answer {items, total, page, perPage}.
  • Roles (owner, administrator, editor, author, contributor) and what each may do: docs/API-PERMISSIONS.md. Entries come with a can object so the editor greys out what the user may not do; the server checks every action again.

Collections and entries

Collections come from the site's markstage.config (@markstage/core/site-config; the same file the editor reads in dev): url and group there may be functions of {id, data}, where data is the frontmatter or JSON. An entry's own URL field (fields.url) wins over url. A url or group function that throws gives url: null / no group for that entry, logged on the server. A site without a markstage.config lists collections in the server's config.json, with url as a template (/blog/{slug}/).

Field schema. The site config may say schema: { keystatic: './keystatic.config.ts', options } (options as for core's keystaticSchema: rich, multiline, url, collections, roles). Each JSON collection gets the Keystatic collection with the same folder (else the same name). Its changes saves then parse with {schema, policy: keystaticPolicy}: inserted values take the schema's key order, empty values are left out as Keystatic leaves them out, and the file stays byte-identical to Keystatic's own Save (proven on the real site: 41 of 41 pages after an insert). Without core's JSON engine such a save answers 503 instead of writing a non-Keystatic file. Keys the server owns (draft, publishAt, protected) are kept even though Keystatic's schema may not list them; a site that edits these files in Keystatic too should add them to its schema (fields.ignored()), or a Keystatic save drops them.

GET collections/:c/schema → {entry: Field} (core's schema descriptor: {type: 'object', fields}, with array, conditional, text, select, image, relationship… fields). 404 {error: 'no-schema'} when the collection has none.

GET collections → [{id, label, format: 'md'|'json', hasStatus: bool, counts: {all, draft, scheduled, published, trash}, can: {create}}].

GET collections/:c/entries → list. Query (all optional, all reflected in the editor's URL): status=draft|scheduled|published, author=<authorSlug>, tag=<tag>, q=<search in title, slug, excerpt>, group=<groupId> (the section or topic, docs/CONFIG.md groups), since=<ISO date> (changed at or after it), attention=no-description|no-title|alt-text|links|not-translated (the lists screen's "Needs attention": only what the server already has, the search title and description from the fields, the publish rules' image and link findings, and the tracked locales' words; an unknown one is 400), sort=<column> or -<column> (newest or Z first) for any column: title, date, modified, publishAt, status (draft, scheduled, published), author, url, group, id, words (default -modified; an unknown one is 400). Text sorts ignore case and put numbers in order; ties are in id order both ways. page, perPage. Item = {id, title, status, author, tags, date, modified, publishAt, url, version, excerpt, group?, groupId?, words?, parent?}. groupId: the group the entry is in (its collection's groups.field, docs/CONFIG.md groups), only for a collection with groups; null when it names none. locales: [{code, done}] is there when the site tracks locales with their own title or description ("Translation status"): done is that locale having its words (or sharing the source's language, where none means "the same"); outdated words are not told here (that needs git history: the translations list). words: an article's (Markdown) length, the words of its text without the frontmatter, HTML tags or Markdown marks. group is there only when the site's markstage.config gives the collection a group({id, data}) function and it returns a value (on the pilot site: the cluster title). The editor's search groups results by it. The answer also has counts (per status, for the filter chips, ignoring the status filter) and facets: {authors: [{name, count}], tags: [{name, count}]}: every author and tag in the collection, whatever the filters, for the lists screen's choices.

  • Save (PUT): md: the server runs docToMd(doc, currentText) (surgical), then applies frontmatter key changes ({key: value}; null removes a key) surgically; json: changes is a list of operations applied in order by the core JSON engine (JsonEntry: only the changed characters move, formatting kept): {path, value} or {op:'set', path, value}, {op:'remove', path}, {op:'insert', path:'sections', index, value}, {op:'move', path:'sections', from, to}, {op:'duplicate', path:'sections', index}. Paths are dotted (sections.3.value.heading); __proto__, prototype and constructor segments are refused. data (a whole object) is also accepted but rewrites the file. The file is written and committed with the signed-in user as git author. changedBlocks = blocks the save rewrote (0 = byte-identical, and then nothing is committed). commit = the new commit sha or null.
  • The address changes only through Move. A save of any kind (PUT, source, publish, revision restore, find and replace, bulk actions, Categories and tags) that would change the entry's page address (its slug, or a field the address is made of, such as a page's uri or parent) is 422 {error: 'moves', message, from, to}, and in a change across the site that entry is skipped with the same reason. Use the move routes below, which rewrite the links and record the redirects.
  • Links: for every role, any href, src or url attr in the document (link marks, images, box attrs at any depth), in the frontmatter and in JSON entries must be http, https, mailto, tel or relative; anything else (javascript:, data:, vbscript:, file:, ...) is 422 with urls: [...]. Snippets and templates too.
  • Collections without status (pages, settings): PUT saves and commits; the next build ships it. publish on them is the same "Update" as for posts: save (if a body is given) + checks + build + deploy, one job.
  • Saving a published entry changes what the next build ships, so it needs the publish right on that entry; the editor's "Update" button uses publish (below) which saves and deploys in one job.
  • draft, publishAt and protected are not set by PUT or a source save (422): they change only through the publish and protection routes. Non-editors cannot change the author field away from themselves (403).
  • Locks (docs/OPERATIONS.md "Locks"; core's @markstage/core/locks): every save path (PUT, source, publish, revision restore, bulk, compat) compares the stored entry with the saved one. A locked block that was moved, deleted or changed is 423 {error: 'locked', message, blocks: [{what, path, type, label, by, message}]}, for every role, and nothing is written. what is move, remove, edit or layout; by is 'the site' (the site's rule, markstage.config locks) or 'an editor' (a lock stored in the entry); message is the sentence to show ("The FAQ box is locked by the site: it can't be deleted."). Other blocks may still be moved past a locked one; a move is a change in the order of the move-locked blocks among themselves. Where locks are stored:
    • pages (JSON): _lock: {move?, remove?, edit?} on a section or list item, and _lock: {layout?, edit?} at the top of the entry (layout: nothing added, deleted or reordered; edit: read-only). The site's rules name sections by their discriminant.
    • articles (Markdown): frontmatter locks: [{heading, move?, remove?, edit?}] for the section under a heading (to the next heading of the same or a higher level), and locks: [{box, move?, remove?, edit?}] for every run of that box (by block name; a run of the same box counts as one). A box's own lock attribute (data-lock="move remove") is read too, where a block pack keeps it. The site's rules name boxes by block name.
    • true locks that action; false lifts the site's rule for it on this entry only ("Unlock on this page", e.g. _lock: {move: false, remove: false} on the home hero, or locks: [{box: faq, remove: false}]). A rule binds unless a marker on either side of the save lifts it. A page section lifted and deleted in the same save reads as a plain delete (its marker leaves with it): lift it first. An article's box lock outlives the box, so there it may be lifted in the same save.
    • by and at on a marker say who set it and when. The server writes them on every marker a save adds or changes (the person's name, the time to the second), whatever the editor sent.
    A lock binds when both the stored and the saved entry have it, so an editor may take one off and change the block in the same save. Adding, taking off or changing a lock needs editor or above (403 naming the block); each one is audited as entry.lock or entry.unlock {commit, change, block, path, from, to, rule?} (rule: 'site' when it lifts a site rule or puts it back; a change that both lifts and adds is entry.lock with change: 'change'). _lock and locks cannot be set by bulk actions. Without @markstage/core installed, a save of an entry with locks (or of a collection the site's rules cover) is 503 locks-unavailable, never let through.
  • The site's rules (Settings → Locks): GET site/locks (anyone signed in) → {rules: {pages: {<type>: {move?, remove?, edit?}}, articles: {…}}, kinds: {pages: [{type, label}], articles: [{type, label}]}, version, source: 'config'|'file', file}. kinds are the section types the site's pages use (discriminant) and the boxes its block packs define, so a rule can be added for any of them. These are the rules saves are checked against now: the editor reads them here, not from its build. PUT site/locks {rules, version} (owner, administrator; rules in either form, {hero: ['move']} or {hero: {move: true}}) → {rules, version, source: 'file', commit}; 409 on a stale version, 400 on a wrong shape (in words), 403 below administrator, 503 without core. The rules are written to markstage.locks.json at the site's root (list form, keys sorted), committed as "Lock rules for every page" with the person as author, and audited as site.locks {commit, from, to, was}. From then on the file wins over markstage.config locks (code is never rewritten from a screen); the same rules again commit nothing.

Move (rename) an entry

POST collections/:c/entries/:id/move {version, newId, newSlug?} → 200 (draft) or 202 (live, with a build and deploy job) {id, version, url, oldUrl, linksUpdated: [{collection, id}], redirects: [{from, to}], repointed: [{from, to}], commit, job}.

  • One commit: the file gets its new name. Its slug follows when it was the same as the old name, or is set to newSlug. Every entry that links to the old address then links to the new one, and the site's redirects hook records old → new.
  • Links are rewritten surgically, through core:
    • frontmatter through setFrontmatter (only the changed keys);
    • the Markdown body through the doc (only the changed blocks);
    • JSON through the JSON engine (only the changed values).
  • A link is a string value that is the old address in any locale (/x/, /en-us/x/), with or without the trailing slash, as a site path or an absolute siteUrl URL, keeping any #hash or ?query. An href inside HTML strings counts too. Visible text (text values) is never changed.
  • Redirects: the site's redirects hook (below, "Redirects") gets {"redirects": [{from, to}, …]}: one pair per locale, as site paths. The files it changes go into the same commit. When the hook can list, no chain or loop is made: redirects that pointed at the old address now point at the new one (repointed: [{from, to}] in the answer), and a redirect away from the new address is removed (a page is there again). If the hook fails: 502 {error: 'redirects-failed'}, nothing is moved, and its own changes are undone. With no hook, no redirects are written.
  • Rights: as for a save, and a live entry (published, or any entry of a collection without status) needs the publish right. 409 {error: 'id-taken'} if newId exists, 409 {error: 'address-taken', url, entry} if the new address is another entry's (in any collection), 409 on a stale version, 422 for a bad name, and validate runs on the renamed entry.
  • If the job fails, every file of the move commit goes back to its text before the move (except a file someone changed since, which the log names). The live site keeps the old address.
  • The mover's autosave follows the entry to its new id.

Move many entries at once (the Pages tree)

POST site/move {moves: [{collection, id, version, newId?, newSlug?, parent?, set?: {field: value|null}}], dry?} (1 to 200) → 200, or 202 when a live entry changed (one build and deploy job) {commit, moved: [{collection, id, from, version, url, oldUrl}], linksUpdated: [{collection, id}], redirects: [{from, to}], job}.

  • Pages dragged in a tree: a new name (newId, newSlug, as for one move), and fields to set (order, the parent or group field the address is made of; never a status key, page code, the title, slug or url field). An entry whose address changes moves like one move does: every link to the old address follows and the redirects hook records old → new in every locale.
  • Pages whose address is a field of their own (fields.url, such as uri) move by parent: the id of the page to go under, or "" (or "/") for the top level; set (such as order) rides along. The server works out the new address (the parent's address and the page's last segment; one sent by the browser is never taken), and every page of the same collection under the old address follows, keeping its place below it. Each page gets its own redirect in each locale (no prefix rule), and the answer's moved lists them all, a page before the pages under it. Refused: the home page / ("The home page stays where it is."), a page under itself or under a page below it, a parent that is missing or moves in the same request, a page below listed on its own ("It moves with “X”, the page it is under: leave it out."), and a collection whose addresses come from names (move those by name).
  • A page that entries of another collection live under is not moved, by parent or by a new name, until they are: "5 posts live under /blog/; move them first." Its own collection's pages under it follow only with parent.
  • dry: true makes every check and writes nothing: 200 {dry: true, moved: [{collection, id, from, url, oldUrl}], linksUpdated: [{collection, id}], links, redirects: [{from, to}]}, the same lists the move itself would give (links: how many entries would have a link rewritten). A refusal is the same 422. A key a move does not know (misspelt, or dry put on one move) is refused: "“dry” is not part of a move."
  • An old address a page comes back to is not taken: the redirect from it goes, and a redirect to an address that moves is pointed at the new one, as for one move.
  • In such a collection the list (GET collections/:c/entries) gives each entry parent: the id of the page whose address is the longest one the entry's address starts with (never the home page), or null at the top level.
  • Every move is checked first (the version, the name, the fields, the rights as for a save, the publish right for a live entry whose address changes, the site's validate). If any one cannot be made, nothing is written: 422 {error: "invalid", problems: [{collection, id, message}]}. A name another entry has, or another move takes or leaves, is refused, and so is a new address that another move in the same request leaves (it would make a chain): move those one after the other. A new address another entry has (in any collection), or that two moves both go to, is refused too.
  • One commit (Move N entries), audited as entries.move. A failed build or deploy puts back every file of it that nobody changed since, like one move.

Publish, schedule, unpublish (status for a static site)

Status lives in the entry itself, so the site's build decides what is live (see "Site-side contract"):

statusmd frontmatter / json top-level keys
draftdraft: true
scheduledno draft, publishAt in the future
publishedno draft, no publishAt or publishAt in the past

Held. When a scheduled entry falls due and the publish rules stop it (it was edited after it was scheduled), the scheduler holds it: draft: true is added and publishAt kept, in a commit by "Markstage scheduler", so the site's build leaves it out; the server records why. The API still says status: 'scheduled', with held: {dueAt, reasons} on the entry and in lists. Every scheduler run checks held entries again: once nothing stops one, that run clears draft and publishAt and puts it live (schedule.released); a failed deploy holds it again. Publish (with or without anyway), unpublish or a new schedule ends the hold.

Failure rule (also in SECURITY.md): jobs run one at a time. If the checks, the build or the deploy fail, the deploy step has not completed, so the live site keeps the previous deploy (the site's deploy command must be atomic, e.g. upload then switch). The server then makes a revert commit that puts the file back to its text before the job, and stores the attempted text as the user's autosave for that entry, so nothing they wrote is lost and the repo again matches what is live. The job ends failed with the log.

When a failed build or deploy names entry files in its output (e.g. Astro's Location: …/src/content/blog/x.md), error says which: The build step failed on posts/x (src/content/blog/x.md). The live site was not changed. (up to three entries; otherwise just the step).

Presence and the soft lock

Who has an entry open, and who is editing it, so two people see each other before a save runs into a 409. Site-side contract (static sites)

  1. Collections with hasStatus filter in the site's content queries: entry.data.draft !== true && (!entry.data.publishAt || new Date(entry.data.publishAt) <= buildTime). For example: add draft: z.boolean().default(false) and publishAt: z.coerce.date().optional() to the blog schema and one isLive(post) helper used by every getCollection('blog', ...) call (lists, sitemap, RSS, related posts, getStaticPaths).
  2. The build command must exit non-zero on failure; the deploy command must be atomic and exit non-zero on failure.
  3. MARKSTAGE_BUILD_TIME (ISO) is set for the build so scheduled posts appear at the right build.
  4. Entries with protected: true are built to a private folder (protectedPages.dir), never to the public output, and are left out of every derived output: sitemap, RSS, llms.txt, llms-full.txt, the per-page Markdown twins (/<page>.md, and any other copy a site makes), link-card JSON and site search (the rehearsal found all of these leaking for a protected page). The web server sends requests it cannot find in the public output to Markstage, or guards the private location with auth_request /markstage/page-auth (tested files: deploy/nginx/; use try_files $uri $uri/index.html ..., not $uri/). For example: protected: z.boolean().default(false) in the blog and pages schemas, and isLive() plus the sitemap and feed filters skip protected entries.
  5. Preview: the site's dev server runs with MARKSTAGE_PREVIEW=1. Then isLive() is true for every entry (drafts and future posts render), so a writer can preview a draft. The dev server must start with every entry valid against the site schema: one invalid entry stops it (the preview page shows the site's message).
  6. Link cards: when the site config has editor.linkCards (core: a site path such as /link-cards.json, or {url, fields}), the editor fetches that path from its own origin. The server answers exactly that path on the CMS origin (GET/HEAD only, .json, at most 5 MB) with the file from the last build in verify.public, and 404 before there is one (the editor then shows what it knows of the page). Nothing else outside the base path is served. Keep protected entries out of that file (point 4).

Server-side converter interface (packages/core)

The server calls core through one adapter (packages/server/src/content/converter.mjs), stubbed in tests: @markstage/core: createConverter({packs}) → {mdToDoc, docToMd (surgical), changedBlocks, rawHtmlOf} and readFrontmatter(text) → object; @markstage/core/json: JsonEntry (set/remove/insert/move/duplicate). Block packs the converter needs are listed in the server config (packs: absolute paths to modules whose default export is a pack or a list of packs). Still wanted from core: setFrontmatter(text, {key: value|null}) → text (surgical YAML for the settings drawer); until then the server writes changed top-level keys as single-line JSON values (valid YAML) and leaves every other line untouched. Without core installed, Markdown routes answer 503. @markstage/core/locks (also from @markstage/core): checkLocks(before, after, rules) → violations, lockChanges(before, after, rules) → [{change: 'lock'|'unlock'|'change', path, type, label, from, to}], lockReport(…) → {violations, changes} and lockOf(v) (a stored or configured lock to {move?, remove?, edit?}); a side is a page {data} or an article {doc, frontmatter}, rules the site's locks (see "Locks" above). The editor can run the same function before a save, to show what the server would refuse.
