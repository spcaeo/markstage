Importing entries and media

Bring entries and media files from another system as JSON: a dry-run plan first, nothing written or fetched, then the run of that plan as one job.

Part of the API contract (docs/API.md: its conventions, prefix and errors apply here). Entries and media files from another system, sent as JSON: first a plan (a dry run, nothing written or fetched), then the run of that plan, as a job. Server code: packages/server/src/import/.

  • Idempotent on the source's ids. Each entry and media file carries the id it has in the source (sourceId). What an import made is remembered by source + sourceId: the same payload again changes nothing; a changed one updates what the first made; a new id makes a new entry.
  • Never over a person's work. An entry changed in Markstage since it was imported (or deleted) is left alone and the plan says so, unless the payload says overwrite: true.
  • The editor's own rules. Each entry is created or saved through the editor's create and save: rights, links, raw HTML, locks, synced Library copies, the page's address (no move by a save), the site's own validate. In a collection with drafts, an import makes drafts and keeps an entry's status when it updates it: publishing stays a person's step, and the publish rules' findings are listed in the plan so they are known before then.
  • Media through the guard. Files are fetched by the server through the same SSRF guard as the Library's import (public addresses only, checked after DNS and on every redirect, ports 80 and 443, size and time limits; docs/SECURITY.md "Fetching from the web"), then go through the upload's pipeline (sniffed, never SVG, re-encoded), all in one commit.
  • Editors and up.

The payload

{
  "source": "wordpress",
  "overwrite": false,
  "mediaAs": "url",
  "media": [{ "sourceId": "att-41", "url": "https://old.example.com/wp-content/uploads/truck.jpg", "alt": "Our truck" }],
  "entries": [
    { "sourceId": "post-12", "collection": "posts", "title": "Moving day", "id": "moving-day",
      "frontmatter": { "author": "alice", "tags": ["news"], "image": "media:att-41" },
      "body": "# Moving day\n\nWe moved. ![Truck](media:att-41)\n" },
    { "sourceId": "page-3", "collection": "pages", "title": "About", "data": { "uri": "/about-us/", "sections": [] } }
  ]
}
KeyWhat
sourceWhere it comes from: lowercase letters, digits and hyphens. Ids are remembered per source.
entries[]At most 500. sourceId (text, at most 200, once per payload), collection, title (or the collection's title field in frontmatter / data), and id (optional: else made from the title, as a new entry's is). A Markdown collection takes frontmatter and body (Markdown, at most 1 MB); a JSON one data. draft, publishAt and protected are refused: an import brings drafts.
media[]At most 200. sourceId, url (http or https), alt.
mediaAsHow an entry names a stored file: url (default: its address on the site from the media URL template, /uploads/2026/10/truck.jpg) or relative (a path from the entry's file, ../../assets/uploads/2026/10/truck.jpg, as an Astro image() field takes it).
overwritetrue: replace entries a person changed or deleted since they were imported.

In every text of an entry (the body, and every string in frontmatter or data), media:<sourceId> and each media file's own url become where that file is on the site. An entry naming media:<id> that the import does not bring in is a problem for that entry. The payload is a request body, so at most the server's maxBodyBytes (4 MB by default): split a larger import into several.

Routes

Method + pathAnswer
POST importthe payload → 201 {run, entries, media, counts}: the plan, kept for an hour
POST import/:rid/run{} → 202 {run, job}. The person who made the plan, once, within the hour (403, 409, 410 expired)
GET import/:rid{run, plan, result} (result once the job is done)
GET import{items: [run]}, the newest 50

run: {id, source, status: planned|running|done|failed|expired, createdAt, expiresAt, by: {id, name}, job, finishedAt}. The job (GET jobs/:id) logs each item; its steps are media and entries.

The plan

Each entry: {sourceId, collection, id, action, problem?, rules?}.

actionWhat the run would do
createmake a new entry (a draft where there are drafts)
updatesave the new text over what this import made before
unchangednothing: the payload and the entry are as before
skipnothing: problem says why (no such collection, no title, a status key, the address taken, an unsafe link, raw HTML, a locked block, the site's validate, changed or deleted in Markstage since)

rules: the publish rules' findings for the new text ([{rule, level: block|warn, message}]): what will stop or warn when a person publishes it.

Each media file: {sourceId, url, action: fetch|reuse|skip, path?, problem?}. reuse: the file this source id brought in before is still in the media library at the same address; nothing is fetched. path for a fetch is where it would go; the run's result has where it went. Nothing is fetched for a plan.

The run

The run makes the plan again at its time, from the same payload, and does what it says: first the media (one commit: "Import 3 media files from wordpress"), then each entry (a commit each, by the person, audited as entry.import). A problem with one item is that item's (result.entries[i].problem); the rest go on. result.counts: {create, update, unchanged, skip, problem}. Audit: import.plan and import.run with the counts.

Tests: import.test.mjs.

Source: docs/API-IMPORT.md on GitHub. Something unclear? Open an issue.
