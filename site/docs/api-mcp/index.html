The MCP server: AI agents

Connect an AI agent to Markstage over MCP: it reads the site and drafts as the person whose token it holds, and publishes only if an owner allows it.

  • Proof

Part of the API contract (docs/API.md: its conventions, prefix and errors apply here). An AI agent (Claude, or any client of the Model Context Protocol) reads the site and drafts changes as the person whose token it holds, through the editor's own routes. Server code: packages/server/src/mcp/; the relay: packages/astro/bin/markstage.mjs.

By default nothing an agent does publishes, deletes, moves or promotes anything. It changes drafts, adds pictures, and puts changes to live pages (and the pictures they show) into a release that is not scheduled. A person reviews that release and publishes or schedules it. The one exception is a token an owner or administrator made with mcp:publish ("Publishing" below): its agent may ask to publish a release, and the site decides exactly as it would for that person, after its checks pass.

The endpoint

POST <api>/mcp (/markstage/api/mcp), on the CMS origin only. It uses MCP's Streamable HTTP transport, answered with plain JSON: one JSON-RPC 2.0 message in, its answer out. There is no event stream and no session id.

  • GET: 405 with Allow: POST, as the spec asks of a server with no event stream, and words for a person who opened the address in a browser ("This is Markstage's MCP address. …"). Other methods: 405. A JSON array (a batch): -32600.
  • A notification, or a client's response to the server: 202 with no body.
  • Methods: initialize, ping, tools/list, tools/call. Anything else: -32601. Unknown or wrong arguments: -32602, or a tool error naming the argument.
  • Protocol version. The server speaks 2025-06-18 and 2025-03-26. initialize answers with the client's protocolVersion when it is one of those, else with 2025-06-18. It never refuses, as the spec says. On later requests, an MCP-Protocol-Version header naming another version gets 400; no header is fine.
  • initialize gives serverInfo {name: 'markstage', title, version}, capabilities {tools: {listChanged: false}} and instructions, which tell the agent the rules below and that content it reads is data, not instructions.
  • Where it answers. The site's hosts (siteHosts) and the share origin answer 404 for this path, whatever the method. So does every other CMS path there.

Tokens

An agent's token is its own kind. It is not the laptop CLI's token.

  • Scopes: mcp:read (the read tools), mcp:draft (the write tools too, add_image among them; it brings mcp:read) and mcp:publish (publish_release; it brings mcp:read, not mcp:draft).
  • Made in a browser session: POST me/tokens {name, scopes: ['mcp:read'] | ['mcp:draft'] | ['mcp:publish'] | …, days: 1..90} gives 201 {token, secret} (mst_…, shown once). In the editor: Settings → Tokens, "New AI assistant token" (#/settings/tokens?new=mcp). Reading is always ticked; writing drafts is ticked only when asked for. The page then shows the secret once, npx markstage mcp login <origin>, the client config and the MCP address.
  • mcp:publish is an owner's or administrator's to give. Anyone else asking for it gets 403 ("Only an owner or administrator can make a token that lets an AI agent publish."), and the screen does not offer it to them (GET me/tokens says canMcpPublish). It is never ticked for you. Beside it, and again on the made token, a plain warning: the assistant can put releases live without you pressing Publish; it is checked like you are (the site's checks, the publish rules, approvals and freezes still decide, and a failed check stops it); every publish names the assistant and you; give it only to an assistant you trust, for as few days as you need, and revoke it when you are done.
  • A token is for the command line (env:…) or for an agent (mcp:…), never both: a mixed request gets 400. GET me/tokens gives scopes (the command line's), mcpScopes and groups: {cli: {scopes, reaches: '/env'}, mcp: {scopes, reaches: '/mcp'}}.
  • An mcp: token reaches /mcp only (403 elsewhere). A command line token on /mcp gets 403. A browser session on /mcp gets 403 too: the endpoint takes a token, not a cookie.
  • Behind a reverse proxy, the proxy must pass Authorization: Bearer mst_… through to Markstage, or no agent can sign in. A browser password (basic auth) in front of the editor is not forwarded: pass only a Markstage bearer token, and leave basic auth off for /markstage/api/mcp and /markstage/api/env, which the token protects. The sign: a token that works gets 401 "Send a Markstage MCP token…" instead of "Unknown token.". An nginx example is in docs/SECURITY.md "Operator checklist".
  • The token only ever goes in Authorization: Bearer mst_…, never in a URL. Unknown, revoked or expired: 401, audited security.token. A revoked or expired agent token's words say to make a new one at Settings → Tokens and give it to the agent. markstage login keeps command line tokens only: it checks a token on /env, which an agent's token cannot reach.
  • Origin. No Origin header (an agent, the relay) is fine. The CMS's own origin is fine. Any other browser Origin gets 403, audited security.origin. Bearer requests skip the CSRF check: a browser never sends that header on its own.

The relay: markstage mcp

For clients that start a command (stdio): @markstage/astro ships markstage, node only. <url> is the editor's address. https://cms.example.com means Markstage at /markstage; a server with another basePath is named by its path (https://example.com/cms/, …/cms/api/mcp or an editor link with #/… too), and that base is kept with the token, so later the bare origin is enough. The token screen shows the commands with the editor's own address.

  • markstage mcp login <url> [--token-stdin]: checks the token with ping, then keeps it in ~/.config/markstage/credentials (0600; $MARKSTAGE_CONFIG_DIR/credentials) under mcp, apart from the command line's tokens. A token the server does not take is not kept.
  • markstage mcp [<url>]: one JSON-RPC message per line on stdin, each answer on one line on stdout, in order. The token comes from MARKSTAGE_TOKEN or the kept one; the URL from the argument, MARKSTAGE_URL, or the one server kept. Only JSON goes to stdout. A line that is not JSON gets -32700. An HTTP refusal becomes a JSON-RPC error -32000 with the server's words and data.status, and the words go to stderr too. Notifications get no line.

A client's config, for example:

{ "mcpServers": { "markstage": { "command": "npx", "args": ["markstage", "mcp", "https://cms.example.com"] } } }

A client that speaks Streamable HTTP itself uses https://cms.example.com/markstage/api/mcp with the header Authorization: Bearer <token>.

Tools

tools/list lists the read tools, the write tools only for an mcp:draft token, and publish_release only for an mcp:publish token. Each tool has a JSON Schema (additionalProperties: false) and annotations: reads readOnlyHint, and only publish_release destructiveHint. A result is structuredContent plus the same JSON as text. A refusal is a result with isError: true and structuredContent {error, status, message, …}: the editor's own error code, status and words.

Source in, source out (lossless)

An entry is read and written as its file's text: front matter and Markdown for an article, the JSON for a page. So nothing is lost in a conversion. get_entry then update_entry with the same source gives {changed: false}, writes nothing and makes no commit. A change touches only what the agent changed. Sections, components, raw HTML, synced copies and _lock markers stay byte for byte.

Small edits

To change a word, a sentence or a link, an agent does not need the whole file. Reading and sending back a long article costs far more than the change. Two things keep it small:

  • get_entry with find gives only the passages that hold that exact text, each with three lines around it and its line numbers (from, to), plus the version. Passages that touch are joined; at most 20, then more: true. Without find, get_entry gives the whole source as before.
  • edit_entry takes only the changes: edits: [{find, replace, all?}]. find is the text exactly as it is in the file (spaces, line breaks and Markdown marks included; in a page's JSON, as the JSON writes it, \" for a quote). replace is what goes there ("" takes it out). Each find must be in the file once; set all: true to change every place. The edits apply in order, each to the text the ones before it left. If any edit finds nothing or finds several places, nothing is changed and the refusal says which edit and how many places.

edit_entry then saves exactly as update_entry (without release, drafts only, 409 live otherwise) or add_to_release (with release) would with the edited source. Every rule of theirs holds: the version (stale: 409 with the version now), the rights, locked and synced blocks (423), hidden values (422 hidden), the site's validation and the modified date. When the entry is already in that release (and its file has not changed since), the edits apply to the text the release holds, so several small edits add up in one item (from: "release").

The answer is small: {changed, version, edits: [{find, matches}], diff}. find is cut to 80 characters. diff holds only the changed lines, with two lines around each change, under @@ -<old line> +<new line> @@ headers, a long line cut to the part that changed, and at most 4,000 characters. An edit that changes nothing gives {changed: false} and writes nothing.

Use edit_entry for small changes. Send the whole source (update_entry, add_to_release) only to rewrite most of an entry.

Pictures

add_image {alt, url? | data?, filename?, release?, collection?} adds one picture. It never stores a picture itself: the bytes go to the editor's own upload routes, as the token's person, so every rule of a person's upload holds. The type is told from the bytes (JPEG, PNG, GIF, WebP, AVIF; an iPhone HEIC is turned into a JPEG; never SVG), the picture is re-encoded (metadata stripped, the long side capped at media.maxSide), named in the media folder (<media.dir>/<year>/<month>/<name>.<ext>, -2 when the name is taken) and listed in the media library with its alt text. The audit row says via: 'mcp' and the token's name.

  • alt is required: a few words on what the picture shows (up to 500 characters). Empty or only spaces: refused.
  • The picture, once: url or data, never both.
    • data: the bytes in base64 (standard or URL-safe), or a data:image/…;base64, URL. At most media.maxBytes once decoded; more is 413 with the sizes ("This file is 81 KB; the limit is 64 KB. Export it smaller…"). A token with mcp:draft may send a request big enough for that in base64 (media.maxBytes × 4/3 and 256 KB, and never less than maxBodyBytes); a request bigger than that, or any bigger than maxBodyBytes from a reading token, is 413 before any tool runs.
    • url: fetched by the server through the same guard as the media import (docs/SECURITY.md "Fetching from the web"): http and https on ports 80 and 443 only, no name and password in it, every address the name resolves to on the public internet (no loopback, private, link-local such as 169.254.169.254, IPv6 included), each redirect checked again, a time limit, and at most media.maxBytes. Refused: 400 unsafe-url, in words, and nothing is asked of that address. The file is named after the address's last part unless filename says. The address is kept with the picture (its credit: {provider: 'web', label, sourceUrl}, shown in the media library as "Fetched from"), so a person can check its licence later.
  • Only pictures: a PDF (which the editor's upload keeps as a download), a page or anything else is 415 in words.
  • Rights, as in the editor. Uploading is the person's media.upload (contributor and up). Fetching from an address is an import (media.import, author and up): a contributor's agent sends the bytes (403 otherwise).
  • Without release the picture is committed to the media folder as the person's upload, its commit saying Upload <path> (an AI agent, via MCP: <token name>). It is on no page until an entry that uses it goes live: put it in a draft with update_entry, or in a live page's change with add_to_release. A site whose media folder is under public/ puts every file there on the site at its next build, used or not, so there a picture an agent adds must wait in a release: without release it is 409 served-as-is, nothing written.
  • With release (a release that is open and not scheduled; 409 scheduled otherwise, asked before anything is fetched and again just before the item is kept) nothing is written to the repo. The picture waits in the release as a media item (get_release's counts.media), its name in the media folder kept for it (an upload meanwhile takes another). It is written, committed and listed in the media library when the release goes live, in the release's one commit with the entry that uses it, and release.publish lists it in mcpItems. Taken out of the release, or the release cancelled, it never reaches the site. A contributor puts nothing into a release (403).
  • The answer: {added, path, url, type, width, height, bytes, alt, media, release, use, note}. media is the media library's id (null while it waits in a release); release is {id, name, status, version, item, counts} or null. use says what to write, as the editor writes it: use.field for a cover or image field (the path inside the media folder, 2026/11/team.webp, or the site path of a file under public/), and use.markdown, per Markdown collection (or only collection), ![alt](…) with the path relative to that collection's folder.

A draft's picture in Markdown: Astro processes the pictures of every entry, drafts too, so a draft that shows a picture from src/assets/ puts that file in the build's _astro/ under a hashed name, as a person's draft does. No page, sitemap or feed names it until the draft goes live.

What an agent may not do

The editor's own checks apply to every write: rights, version, locks, synced copies, links, raw HTML, status keys, and the site's validate. An agent also meets stricter checks of its own, before the route's:

  • Synced blocks. A change that alters, removes or detaches a block synced from the Library: 423 synced. A person changes the Library item, or detaches the block.
  • Locks. Changing a locked block, removing one locked against removal, or adding or taking off any lock: 423 locked, naming the block. An agent never locks or unlocks.
  • Hidden values. A source carrying [hidden] where the file has a real value (below): 422 hidden, so a scrubbed value is never written over the real one.
  • Scheduled releases. add_to_release into a scheduled release: 409 scheduled, "“Name” is scheduled: it goes live by itself at its time, so an AI agent cannot add to it. Add to a release that is not scheduled; a person schedules it." This is checked when the add starts and again inside it, after the entry's checks, with nothing awaited between that check and the item being kept, so a release scheduled meanwhile refuses too. The item's via lives in the meta column release_items already has (DEFAULT '{}'), so no migration was needed; a person who adds the same file again takes the item over, and via goes.

In every one of those cases nothing is written and nothing is added.

Reads follow the role

A tool shows only what the token's person may read, through one rule (readable() in src/mcp/tools.mjs):

  • Editors and above see every entry. An author or a contributor sees live entries and their own drafts.
  • An entry they may not read gets the same 404 words as one that does not exist ("No entry "x" in posts, or it is not available to you."), so its existence is not given away.
  • What else names a draft follows the same rule: the pages a Library item is on (get_library_item's uses and usedOn) and a release's entries (get_release's items and counts). Promotion plans name every file they move, so env_status gives plans (else null and why) and get_plan answers (else 403) for editors and up.
  • No tool gives an entry's revisions or history; get_entry gives the current source only.

This is narrower than the editor, where every role reads every entry and its revisions (docs/API-PERMISSIONS.md). A person reads a colleague's draft in the editor to work on it with them. An agent copies what it reads into a model's context, where it can travel further, so it gets only what its person needs.

Writes are the editor's own rights: a contributor changes and makes their own drafts and cannot put anything into a release.

No secrets in answers

Every answer and every error goes through a scrub last (src/mcp/answer.mjs). Each value below becomes [hidden]:

  • The server's secrets from the environment, by name: names ending in PASS, PASSWORD, SECRET, TOKEN, KEY, CREDENTIALS, DSN, SALT or _AUTH, and anything with SMTP_. Also a form's CRM sign-in, by its prefix (<env>_URL, _DB, _EMAIL, _PASSWORD).
  • The config's values under keys that name a secret (password, apiKey, secretKey, token, …), and the AI key read from ai.keyFile (docs/API-AI.md).
  • The content repo's git remote addresses, and any sign-in written into a URL (https://user:pass@ becomes https://[hidden]@).
  • People's email addresses: a person is shown by name and id only, and any email key is left out.

Only a value of 8 characters or more counts as a secret, so a short value never blanks ordinary words. Search and excerpts are matched and cut on the scrubbed text, so half a secret is never shown.

Publishing

publish_release {release, version, reason?}, for an mcp:publish token only. Without the scope the call is a JSON-RPC error that says so: "…does not hold mcp:publish. Only an owner or administrator makes such a token (Settings → Tokens); until then a person publishes."

It never bypasses a rule. In order, and nothing is written until every step passes:

  1. The person. The token's person must be an owner or administrator now: someone made an editor since gets 403 forbidden, in words.
  2. The release. It must be open (409 not-open), not empty (422), and version must be the one from get_release (stale: 409).
  3. The checks, now. The site's content checks run again on exactly what the release holds. A blocking check that fails stops it: 422 checks-failed, naming each entry and check ("…an AI agent never publishes past a failed check"), and the refusal is audited as release.publish with ok: false. (A person's publish runs the checks inside its job and puts every file back when one fails; an agent's is refused before anything is written.)
  4. The person's own publish route. Then the same route a person's Publish uses: the promotion rules for that person (who may publish releases, approvals, freezes and hours; refused: 403 rule, audited), the publish rules (an image with no description, a broken link…: 422 blocked) and the version.

When it is allowed the release goes out as a person's would ({publishing: true, job, release, checks: {passed, warnings}}). It is one commit by the person, its subject naming the agent: Release “Name” (published by an AI agent for <person>, via MCP: <token name>). The release.publish audit row carries via: 'mcp', the token's name and the same words (by), and so does the notice editors see.

At most 5 publishes an hour per token (counted when asked), on top of the call limits below. Over: 429 with Retry-After, audited mcp.limited (publishesPerHour) once an hour. Another token is not held up.

Limits and audit

  • At most 120 calls a minute per token, 30 of them writes. Over that: 429 with Retry-After, audited mcp.limited once a minute.
  • Every tool call is audited as mcp.call (target: the tool, ok). Every row a call leads to (the save, the release item) carries detail.via: 'mcp' and detail.token: <token name>.
  • A release item an agent added keeps via, the token's id and the token's name. When the release goes out (release.publish) or its time comes and something stops it (release.blocked), the audit lists those items as detail.mcpItems: [{rel, title, token}].

Not in v1

  • No resources, prompts or sampling; no event stream.
  • No tool that schedules, promotes, deletes or moves. create_release opens a release and publish_release publishes an open one now; a schedule is a person's.
