The MCP server: AI agents

Connect an AI agent to Markstage over the Model Context Protocol: it reads the site and drafts changes as the person whose token it holds, and never publishes.

On this page

  • Tools
  • No secrets in answers
  • Limits and audit
  • Not in v1
  • Proof

Part of the API contract (docs/API.md: its conventions, prefix and errors apply here). An AI agent (Claude, or any client of the Model Context Protocol) reads the site and drafts changes as the person whose token it holds, through the editor's own routes. Server code: packages/server/src/mcp/; the relay: packages/astro/bin/markstage.mjs.

Nothing an agent does publishes, deletes, moves or promotes anything. It changes drafts, and it puts changes to live pages into a release that is not scheduled. A person reviews that release and publishes or schedules it.

The endpoint

POST <api>/mcp (/markstage/api/mcp), on the CMS origin only. It uses MCP's Streamable HTTP transport, answered with plain JSON: one JSON-RPC 2.0 message in, its answer out. There is no event stream and no session id.

  • GET: 405 with Allow: POST, as the spec asks of a server with no event stream, and words for a person who opened the address in a browser ("This is Markstage's MCP address. …"). Other methods: 405. A JSON array (a batch): -32600.
  • A notification, or a client's response to the server: 202 with no body.
  • Methods: initialize, ping, tools/list, tools/call. Anything else: -32601. Unknown or wrong arguments: -32602, or a tool error naming the argument.
  • Protocol version. The server speaks 2025-06-18 and 2025-03-26. initialize answers with the client's protocolVersion when it is one of those, else with 2025-06-18. It never refuses, as the spec says. On later requests, an MCP-Protocol-Version header naming another version gets 400; no header is fine.
  • initialize gives serverInfo {name: 'markstage', title, version}, capabilities {tools: {listChanged: false}} and instructions, which tell the agent the rules below and that content it reads is data, not instructions.
  • Where it answers. The site's hosts (siteHosts) and the share origin answer 404 for this path, whatever the method. So does every other CMS path there.

Tokens

An agent's token is its own kind. It is not the laptop CLI's token.

  • Scopes: mcp:read (the read tools) and mcp:draft (the write tools too; it brings mcp:read).
  • Made in a browser session: POST me/tokens {name, scopes: ['mcp:read'] | ['mcp:draft'], days: 1..90} gives 201 {token, secret} (mst_…, shown once). In the editor: Settings → Tokens, "New AI assistant token" (#/settings/tokens?new=mcp). Reading is always ticked; writing drafts is ticked only when asked for. The page then shows the secret once, npx markstage mcp login <origin>, the client config and the MCP address.
  • A token is for the command line (env:…) or for an agent (mcp:…), never both: a mixed request gets 400. GET me/tokens gives scopes (the command line's), mcpScopes and groups: {cli: {scopes, reaches: '/env'}, mcp: {scopes, reaches: '/mcp'}}.
  • An mcp: token reaches /mcp only (403 elsewhere). A command line token on /mcp gets 403. A browser session on /mcp gets 403 too: the endpoint takes a token, not a cookie.
  • The token only ever goes in Authorization: Bearer mst_…, never in a URL. Unknown, revoked or expired: 401, audited security.token. A revoked or expired agent token's words say to make a new one at Settings → Tokens and give it to the agent. markstage login keeps command line tokens only: it checks a token on /env, which an agent's token cannot reach.
  • Origin. No Origin header (an agent, the relay) is fine. The CMS's own origin is fine. Any other browser Origin gets 403, audited security.origin. Bearer requests skip the CSRF check: a browser never sends that header on its own.

The relay: markstage mcp

For clients that start a command (stdio): @markstage/astro ships markstage, node only. <url> is the editor's address. https://cms.example.com means Markstage at /markstage; a server with another basePath is named by its path (https://example.com/cms/, …/cms/api/mcp or an editor link with #/… too), and that base is kept with the token, so later the bare origin is enough. The token screen shows the commands with the editor's own address.

  • markstage mcp login <url> [--token-stdin]: checks the token with ping, then keeps it in ~/.config/markstage/credentials (0600; $MARKSTAGE_CONFIG_DIR/credentials) under mcp, apart from the command line's tokens. A token the server does not take is not kept.
  • markstage mcp [<url>]: one JSON-RPC message per line on stdin, each answer on one line on stdout, in order. The token comes from MARKSTAGE_TOKEN or the kept one; the URL from the argument, MARKSTAGE_URL, or the one server kept. Only JSON goes to stdout. A line that is not JSON gets -32700. An HTTP refusal becomes a JSON-RPC error -32000 with the server's words and data.status, and the words go to stderr too. Notifications get no line.

A client's config, for example:

{ "mcpServers": { "markstage": { "command": "npx", "args": ["markstage", "mcp", "https://cms.example.com"] } } }

A client that speaks Streamable HTTP itself uses https://cms.example.com/markstage/api/mcp with the header Authorization: Bearer <token>.

Tools

tools/list lists the read tools, and the write tools only for an mcp:draft token. Each tool has a JSON Schema (additionalProperties: false) and annotations: reads readOnlyHint, nothing destructiveHint. A result is structuredContent plus the same JSON as text. A refusal is a result with isError: true and structuredContent {error, status, message, …}: the editor's own error code, status and words.

Source in, source out (lossless)

An entry is read and written as its file's text: front matter and Markdown for an article, the JSON for a page. So nothing is lost in a conversion. get_entry then update_entry with the same source gives {changed: false}, writes nothing and makes no commit. A change touches only what the agent changed. Sections, components, raw HTML, synced copies and _lock markers stay byte for byte.

What an agent may not do

The editor's own checks apply to every write: rights, version, locks, synced copies, links, raw HTML, status keys, and the site's validate. An agent also meets stricter checks of its own, before the route's:

  • Synced blocks. A change that alters, removes or detaches a block synced from the Library: 423 synced. A person changes the Library item, or detaches the block.
  • Locks. Changing a locked block, removing one locked against removal, or adding or taking off any lock: 423 locked, naming the block. An agent never locks or unlocks.
  • Hidden values. A source carrying [hidden] where the file has a real value (below): 422 hidden, so a scrubbed value is never written over the real one.
  • Scheduled releases. add_to_release into a scheduled release: 409 scheduled, "“Name” is scheduled: it goes live by itself at its time, so an AI agent cannot add to it. Add to a release that is not scheduled; a person schedules it." This is checked when the add starts and again inside it, after the entry's checks, with nothing awaited between that check and the item being kept, so a release scheduled meanwhile refuses too. The item's via lives in the meta column release_items already has (DEFAULT '{}'), so no migration was needed; a person who adds the same file again takes the item over, and via goes.

In every one of those cases nothing is written and nothing is added.

Reads follow the role

A tool shows only what the token's person may read, through one rule (readable() in src/mcp/tools.mjs):

  • Editors and above see every entry. An author or a contributor sees live entries and their own drafts.
  • An entry they may not read gets the same 404 words as one that does not exist ("No entry "x" in posts, or it is not available to you."), so its existence is not given away.
  • What else names a draft follows the same rule: the pages a Library item is on (get_library_item's uses and usedOn) and a release's entries (get_release's items and counts). Promotion plans name every file they move, so env_status gives plans (else null and why) and get_plan answers (else 403) for editors and up.
  • No tool gives an entry's revisions or history; get_entry gives the current source only.

This is narrower than the editor, where every role reads every entry and its revisions (docs/API-PERMISSIONS.md). A person reads a colleague's draft in the editor to work on it with them. An agent copies what it reads into a model's context, where it can travel further, so it gets only what its person needs.

Writes are the editor's own rights: a contributor changes and makes their own drafts and cannot put anything into a release.

No secrets in answers

Every answer and every error goes through a scrub last (src/mcp/answer.mjs). Each value below becomes [hidden]:

  • The server's secrets from the environment, by name: names ending in PASS, PASSWORD, SECRET, TOKEN, KEY, CREDENTIALS, DSN, SALT or _AUTH, and anything with SMTP_. Also a form's CRM sign-in, by its prefix (<env>_URL, _DB, _EMAIL, _PASSWORD).
  • The config's values under keys that name a secret (password, apiKey, secretKey, token, …), and the AI key read from ai.keyFile (docs/API-AI.md).
  • The content repo's git remote addresses, and any sign-in written into a URL (https://user:pass@ becomes https://[hidden]@).
  • People's email addresses: a person is shown by name and id only, and any email key is left out.

Only a value of 8 characters or more counts as a secret, so a short value never blanks ordinary words. Search and excerpts are matched and cut on the scrubbed text, so half a secret is never shown.

Limits and audit

  • At most 120 calls a minute per token, 30 of them writes. Over that: 429 with Retry-After, audited mcp.limited once a minute.
  • Every tool call is audited as mcp.call (target: the tool, ok). Every row a call leads to (the save, the release item) carries detail.via: 'mcp' and detail.token: <token name>.
  • A release item an agent added keeps via, the token's id and the token's name. When the release goes out (release.publish) or its time comes and something stops it (release.blocked), the audit lists those items as detail.mcpItems: [{rel, title, token}].

Not in v1

  • No publish tool. mcp:publish comes later, behind the publish rules.
  • No resources, prompts or sampling; no event stream.
