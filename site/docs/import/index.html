Importing a site from WordPress, Ghost or Prismic

Bring a whole site to Markstage: posts, pages, media, authors, categories and old addresses, with the full plan first and the import run in the background.

On this page

  • Tests

Markstage brings a whole site over in one step: its posts and pages, images and files, authors, categories and tags, search titles and descriptions, and every old address, sent on to the new page. You see the full plan first, with nothing written; then the import runs in the background, in changes you can read one by one in the site's history.

Where: the editor's More tools › Import a site (#/import, editors and up), or markstage-server import on the server. The routes are in docs/API-IMPORT.md ("A whole site"). Server code: packages/server/src/import/ (convert/ reads each format, site/ plans and runs).

Markstage is pre-release. The importers are tested on export files and API answers made from each product's public documentation (packages/server/test/fixtures/import/), and the WordPress importer on one real site's export ("Proof on a real site" below). Ghost and Prismic have not yet been tried on a real site. Check the review list after an import, and tell us what did not come over well.

The steps

  1. Choose where it comes from: WordPress, Ghost or Prismic.
  2. Give the source: upload its export file, or give its API's details.
    • WordPress: the export file (Tools › Export › All content, an .xml file), or the site's REST API (/wp-json/wp/v2). Drafts and private posts need a user name and an application password (Users › Profile › Application Passwords).
    • Ghost: the export file (Settings › Labs › Export your content, a .json file) with the old site's address (an export does not say where the site was), or the Content API with a custom integration's key.
    • Prismic: the repository's name, an access token if it is private, and, if you want the old addresses sent on, each custom type's old address pattern (blog_post=/blog/{uid}/, page=/{uid}/).
  3. Read the plan. One line says it all, for example "142 posts, 18 pages, 1,204 images; 6 slugs already exist (kept both); 31 images need alt text; 4 blocks we could not convert". Below it: what would be created, updated or left alone, the new authors, the old addresses, and tabs for each list (Pages and posts, Images and files, To review, Old addresses). Change where things go and plan again as often as you like. Nothing is written.
  4. Run the import. It runs as a background job (Scheduled & history follows it), in four steps, each its own change in the site's history, by you:
    • images and files, 50 to a change ("Import 50 media files from WordPress (batch 1 of 3)");
    • the new authors, in one change;
    • the posts and pages, 25 new ones to a change; an update (a second run) one change each;
    • the moved addresses, in one change.
  5. Read the report and the review list: each note links to the page or picture to look at.

Everything comes in as a draft in a collection with drafts. A page that was published on the old site is listed as such; publish it when it is checked. The moved addresses go live with the next publish.

What becomes a note instead (in the text as "Import note: …", and in the review list):

  • WordPress: dynamic blocks drawn by WordPress when the page is shown (latest posts, a search box, a calendar); a plugin's block with no HTML of its own; a reusable block (wp:block); shortcodes other than [caption], [gallery], [embed], [video], [audio] and [playlist] (their inner text is kept).
  • Ghost: cards other than image, gallery, bookmark, callout, embed, code, HTML, Markdown, divider, button, toggle, header, video, audio and file (a signup or product card, for example); a members-only post is noted, since here it becomes a normal page once published; a post that was only sent as an email comes in as a draft.
  • Prismic: a slice with no words and no section mapped for it.
  • Everywhere: an embed (a video, a map, a tweet) becomes a link to it; a script, a form, a style or an iframe is left out and noted; a picture from another site stays a link to that site; a link to an old page that was not imported keeps its old address.

Proof on a real site

On 2026-11-04 the WordPress importer ran on the export of a real business site: 148 posts and 17 pages written in the block editor, with 1,513 tables, 1,264 FAQ toggles, 438 call-to-action boxes, code, quotes and a Rank Math SEO plugin. The export was turned into the file Tools › Export writes and imported into a copy of examples/blog, with the old site's uploads served from a local folder. The site itself is not named here, and nothing of it is in the repository.

Entries165 created, 0 failed (148 posts, 17 pages)
Images and files223 brought in, 0 missing
Old addresses594 paths sent to the new pages, 388 ?p= / ?page_id= / ?attachment_id= links kept
Blocks we could not convert0
Notes to review243 SVG pictures still on the old site, 149 JSON-LD blocks left out, 153 pictures without alt text, 4 links to pages that were not imported, 7 other things left out (3 Custom HTML blocks with a script or form, 2 styles, a form, an SVG drawing), 2 pictures on another site
Time7 s for the plan, 31 s for the run; the same import again: under 2 s, nothing changed, nothing fetched

Five posts were checked by hand against their HTML: headings, lists, tables, links (to other posts and to places on the same page), pictures, code, quotes, FAQ toggles, and the front matter (title, dates, author, categories, tags, the search title and description). What it found was fixed, each with a test (import-real-cases.test.mjs): links to a place on the same page, bold inside bold, FAQ questions, [patterns] in code taken as shortcodes, an author the export does not list, and a plan that promised what the run then refused.

What it does not show yet: the export had no embeds (videos, maps), and its posts were the HTML WordPress shows, not the block markup Tools › Export writes, which the fixtures cover. SVG pictures are never brought in (they can carry scripts): save them as PNG or WebP before the old site goes away.

The mapping

Each field goes to the key your collection uses, read from the site's own config: its title, date, author, tags and excerpt roles (fields), its first image setting (the cover and its alt), a categories tags setting, and its seo setting. A JSON collection takes the text as body, the old address in its url field, and mapped slices as sections. The plan's "Where it goes" shows every key, and any can be changed (or left out) before planning again.

{
  "types": { "post": "posts", "page": "pages", "product": null },
  "fields": { "posts": { "excerpt": "summary", "seoTitle": "seo.title", "categories": null } },
  "onCollision": "both",
  "drafts": "skip",
  "media": "used",
  "slices": { "hero": { "section": "hero", "fields": { "heading": "primary.heading", "image": "primary.image" } } },
  "permalink": { "post": "/blog/{slug}/" }
}
KeyWhat
typeseach kind of item to a collection id, or null to leave it out. Default: posts to posts (or the first Markdown collection with drafts), pages to pages, a Prismic type to the collection of its own name.
fieldsper collection, each of title, date, updated, author, tags, categories, excerpt, cover, coverAlt, seoTitle, seoDescription, body, url, sections to a key (dotted for nested), or null
onCollisionan address already taken: both (the new one gets -2), skip (the new one is left out) or replace (it is saved over what is there, through the editor's save: locks and checks hold)
draftsdrafts and private posts, for a collection without drafts: skip or include
mediaused (the pictures the pages show and link to) or all (every file in the export)
slicesPrismic slice types to sections of a JSON collection: {section, fields: {key: 'primary.x' or 'items'}}; a heading alone becomes its words, other rich text Markdown, a picture {src, alt}
permalinkGhost's old address pattern per kind: {slug}, {year}, {month}, {day}

Running it again

An import remembers what it made by the source's own ids (a WordPress post id, a Ghost id, a Prismic document id), for that site. Running the same source again changes nothing and fetches nothing. A post changed at the source is updated; a new one is added. A page someone changed in Markstage since is left alone and listed, never overwritten.

The moved addresses

Every old address of a page, a picture and an author is sent on to its new one. Paths go to the site's redirects hook (docs/API.md, "The redirects hook"), so they appear in Moved addresses and go live with the next publish. A static host cannot match an address by its query, so WordPress's ?p=12, ?page_id=3 and ?attachment_id=41 links are kept in markstage/import/<source>.json in the site's repository, for the site (or its host's rules) to use; a site with no redirects hook finds its paths there too. An address a page of the site already answers is never redirected.

Safety

  • Only public addresses are read. Every request (the API, each picture) goes through the server's SSRF guard: http and https only, ports 80 and 443, the address checked after DNS and again at every redirect, so loopback, private, link-local (169.254.169.254) and other reserved addresses are refused, never contacted (docs/SECURITY.md "Fetching from the web").
  • Limits. An API answer at most 20 MB and 20 seconds, a whole read at most 64 MB and 5 minutes, 50 pages of 100 per list; at most 5,000 entries and 5,000 files an import; an upload as big as the media import allows (64 MB by default, library.importMaxBytes); a picture as big as an upload (media.maxBytes), 15 seconds each.
  • Content types are checked. An API answer must be JSON; a picture must say it is an image or a PDF, and then the upload's pipeline sniffs it (never SVG) and re-encodes it.
  • Nothing that runs comes in. HTML is read into Markdown: scripts, styles, forms, frames and event attributes are dropped (and noted), links keep http(s), mailto, tel or relative addresses only.
  • A credential is used once. An application password, a Content API key or a Prismic token is used for the one read the plan makes, sent only to the source's own address (a redirect elsewhere is asked without it), taken out of any error, and kept nowhere: not in the database, a log, the audit or the plan. On the command line it is read from a file or MARKSTAGE_IMPORT_SECRET, never an argument. Delete the application password at the source when the import is done.
  • The editor's rules. Each entry is created or saved as the editor does it: your rights, links, raw HTML, locks, the site's own checks. Editors and up; each step is audited (import.plan, import.run, entry.import, author.create).

From the command line

On the server itself, as an account named by --as, with the same plan and run (no upload limit):

markstage-server import wordpress ./example.WordPress.2024-05-10.xml --dry --as editor@example.com
markstage-server import wordpress ./example.WordPress.2024-05-10.xml --as editor@example.com
markstage-server import wordpress --url https://www.example.com --user editor --password-file ./app-password.txt --as editor@example.com
markstage-server import ghost ./example.ghost.2024-05-10.json --site-url https://blog.example.com --as editor@example.com
markstage-server import ghost --url https://blog.example.com --key-file ./content-key.txt --as editor@example.com
markstage-server import prismic --repo example-repo --token-file ./token.txt --routes ./routes.json --as editor@example.com

Options: --mapping <file.json>, --on-collision both|skip|replace, --drafts skip|include, --dry (the plan in words, nothing written; the plan also opens in the Import screen at #/import/<id>).

Tests

packages/server/test/import-convert.test.mjs (each converter), import-wordpress.test.mjs (the WXR plan, run, second run, collisions, mapping), import-sources.test.mjs (Ghost's export and Content API, Prismic's recorded answers, WordPress's REST API, the SSRF and credential checks), import-cli.test.mjs, and e2e/import.e2e.mjs (the Import screen on a copy of examples/blog with the WXR fixture).
